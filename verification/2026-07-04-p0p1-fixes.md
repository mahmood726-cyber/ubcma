## §1 — P0 #1: Copas selection never corrected for selection

**File:** `src/ubcma/comparators.py` (`copas_selection`, ~L184–235).

**Bug:** the ρ-grid loop stored no likelihood and selected `best = valid[0]` (ρ=0),
returning the naive REML pool mislabelled as Copas-corrected.

**Fix:** evaluate and store the profile log-likelihood (`res.fun` = −NLL) at each ρ and
select the maximiser (min stored NLL) — the Copas & Shi (2000) MLE over the ρ grid.
Also expose `rho_selected`. At ρ=0 the selection term decouples and μ collapses to the
ordinary RE pool, which is exactly what the old code always returned.

**Verification of behaviour:** under a flat profile (no detectable selection) it
correctly returns the ρ=0 naive fit; under a preferred-ρ it now shifts. `tests/
test_comparators.py` Copas shape tests pass (they assert keys, not μ).

## §2 — P0 #2: field_learned k-fold train/test feature coding inconsistency

**File:** `borrowing/field_scale/field_learned.py` (`build_features`, `gp_fit`,
`predict_kfold`).

**Bug:** each fold re-ran `build_features` on its own subset, so (i) year/log-precision
were standardised by per-subset mean/SD and (ii) `spec_code`/`ma_code` were assigned by
per-subset `np.unique(return_inverse)` — the same specialty/MA could get different
integer codes in train vs test, corrupting the categorical match-kernel and the
distance standardisation for any family with ≥2 specialties/MAs. This drives the
DEFAULT honest k-fold predictions behind REPORT_BORROWING_FIELD §8.

**Fix (frozen transform):** `predict_kfold` now builds the feature matrix ONCE on the
full family block and slices its rows for each fold (`gp_fit(sub_tr, X=X[tr])`), so the
standardisation stats and the category→code mapping are identical for training rows
(`st["X"]`) and held-out rows (`X[te]`). `yz`/`prec` were already corpus-frozen by
`field.prep`; this extends the freeze to log-precision and the two categorical codes.

**Tests:** `test_field_learned.py` fast suite passes (LOO-bruteforce parity, scrambled-
loses, conformal-nominal, kfold-beats-global all green).

**Corrected headline — `benchmark_learned.py` re-run (before-fix run reproduces the
committed JSON exactly, confirming a deterministic baseline; after-fix run below):**

| quantity | before (shipped) | after (fixed) | Δ |
|----------|------------------|---------------|---|
| learned-kernel MAE (honest 10-fold, 5-seed) | 0.332494 | 0.332470 | −2.4e-5 |
| vs within-MA (paired boot) | −0.022973 [−0.03401, −0.01172] | −0.022997 [−0.03401, −0.01171] | −2.4e-5 (stronger) |
| per-regime mid (9–40) | −0.0289 [−0.0546, −0.0035] | −0.0289 [−0.0547, −0.0034] | ~0 |
| per-regime rich (>40) | −0.0218 [−0.0338, −0.0104] | −0.0219 [−0.0339, −0.0104] | ~0 |
| scrambled control | −0.0525 [−0.0673, −0.0373] | −0.0527 [−0.0676, −0.0375] | ~0 (still REAL) |
| conformal cover / width | 0.899 / 1.5533 | 0.899 / 1.5566 | +0.003 width |

**Outcome: the "beats within-MA" headline is CONFIRMED and unchanged to reported (4dp)
precision — the fix if anything strengthens the margin.** The bug was a genuine latent
correctness defect (train/test category-code divergence + mis-standardisation) that
happened to be numerically inert on this corpus because 10-fold splits rarely eliminate
an entire specialty/MA category (the only trigger for `np.unique` re-numbering). It
would bite harder on families where a fold drops a whole category, so the frozen-transform
fix is a real robustness improvement even though no shipped number moved here. The
regenerated `benchmark_learned_results.json` (5th-decimal changes only) is committed as
the corrected-code output; REPORT_BORROWING_FIELD §8 and the manuscript need no edits.

## §3 — P1 (a): survival engine small-k RMST / interval-HR pool

**File:** `rapidmeta-finerenone/rapidmeta-survival-engine-v1.js` (L533 RMST pool,
L589 interval-HR pool) — mirrored in `rmf-deploy/`.

**Bug:** for k<5 used DL τ² (downward-biased for small k; Veroniki 2016) while labelling
the output `fixed_effect_k_lt_5` — a fixed-effect label on a random-effects pool, with a
too-narrow interval.

**Fix:** use REML τ² at every k≥2 (matching the engine's own `reml_hksj` main path and
the no-DL-for-small-k rule); relabel the k<5 fallback `reml_small_k` (honest: small-k RE
advisory, not fixed-effect). The genuine fixed-effect fallback in the main `fit()` path
(L679, `ivPool(...,0)`, τ²=0) is correctly labelled and was left untouched.

**Tests:** `tests/test_survival_engine.mjs` — **68 pass, 0 fail** (both repos). No
fixture/label regression (`fixed_effect_k_lt_5` still asserted for the genuine FE
`fit()` path, which is unchanged).

## §4 — P1 (b): single-arm proportion forest DL τ² with no small-k guard

**File:** `rapidmeta-finerenone/vendor/single-arm-forest.js` (`logitPool`, L50–75; label
L112, L133) — mirrored in `rmf-deploy/`.

**Bug:** logit-scale pool used raw DL τ² at any k≥2 with no small-k guard.

**Fix:** ported the Paule–Mandel τ² bisection solver from the canonical sibling
`vendor/pairwise-pool.js` (which uses PM by default precisely because DL is downward-
biased for small k; Veroniki 2016 / Cochrane v6.5). PM is the small-k guard. Labels
updated DL→PM ("Pooled (PM+RE logit)", "Paule–Mandel random-effects pool").

**Verification:** both files parse; standalone PM-vs-DL check confirms PM is the less-
biased small-k estimator (e.g. k=3 heterogeneous: PM τ²=1.367 vs DL 1.120, wider CI).
No committed numeric artifact / test depends on `logitPool` (panel test does not touch
it). `test_survival_engine.mjs` still 68/68.

**Out-of-scope note (flagged, not silently changed):** the direct companion
`vendor/single-arm-proportion.js` uses the same DL pool (`poolDLRE`) and now differs
from the forest diamond by the DL→PM gap. It was NOT in the flagged defect set; flagged
for a follow-up sync rather than expanding scope here.
